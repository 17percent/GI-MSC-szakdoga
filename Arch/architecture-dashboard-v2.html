Kőbe Vésett Szabályok

Csak .md a repóban: Képfeltöltést, csatolmányt a repóba tenni TILOS. Statikus képek kizárólag az alkalmazás szintű assets mappából renderelődhetnek (D15).
Git-írások sorosítva: Git-írás (commit, push) kizárólag a pg-boss queue-n át, sorosítva történik. Párhuzamos írás, elkerülő út nincs.
UUID Invariáns: A dokumentum identitása a frontmatter id. Ez SOHA nem változhat, átnevezéskor csak a fájlútvonal módosul.
Fizikai törlés tilos: Nincs fizikai DELETE. Minden törlés soft delete (archívum státusz / deleted_at), kivéve a GDPR retenciós ürítést (D20, NY4).
* Ezen elvektől való bármilyen eltérés csak az Architektúra Döntési Napló módosításával lehetséges.

Üzleti Forgatókönyvek & Rendszer-válaszok

Valós szervezeti esetek és azok technikai, adatbázis- és Git-szintű lebonyolítása.

1. Fázis: Aktiválás János szerkeszteni kezd, a backend bejegyzi a locks táblába. 30 mp-enként heartbeat-et kap a kliensből.
2. Fázis: Megszakadás János lecsukja a gépét. Nincs több heartbeat. A backend 5 perc tétlenség után a lock-ot eldobhatónak minősíti. János böngészője a helyi localStorage-ba menti a piszkozatot.
3. Fázis: Kései mentés gát Közben Szabó Mária elkezdi szerkeszteni a kiürült lock miatt. Ha János mégis visszatér és mentene, a backend a baseCommitHash ellenőrzésnél (A4) 412 Precondition Failed hibát ad vissza, megelőzve az ő felülírását.
Rendszerszabály Minden kategória lapos címkeként létezik. Használatban lévő kategória sosem törölhető közvetlenül az adatbázis integritása és a Git-szinkron miatt.
Szekvencia-válasz A backend lekéri a document_categories táblát. Ha van rekord az adott kategória ID-val, az API azonnal megszakítja a folyamatot és 409 Conflict hibát ad, közölve a hivatkozott dokumentumok számát.
Művelet: A felhasználó rányom a Törlés gombra a felületen.
Backend logika: Nem történik fizikai törlés a Postgres-ből vagy a Git-ből. A backend a documents táblában a státuszt archived-ra állítja, a deleted_at mezőt kitölti. A fájl a Git-ben megmarad.
Eseménynapló: Bejegyzésre kerül egy document_archived esemény.
Visszaállítás: Az admin vagy szerző megnyitja a webes Archívum listázó felületét, kiválasztja a fájlt, majd a "Visszaállítás" gombra kattintva a státusz visszaáll draft-ra. Új document_restored esemény generálódik.

# 1. Lépés: Új PostgreSQL szerver indítása a Compose stack-kel

docker compose up -d db

# 2. Lépés: Elsődleges adatok (events, comments) visszaállítása napi backupból

pg_restore -d tudasbazis /backups/db_backup_latest.dump

# 3. Lépés: Helyi Git Clone frissítése

git clone git@github.com:org/tudasbazis-repo.git /volume/clone

# 4. Lépés: A reindex parancs indítása az API konténerből

pnpm --filter backend run db:reindex

-> Eredmény: A 'db:reindex' végigolvassa az összes .md frontmattert, kinyeri az UUID-ket, státuszokat, verziókat és kategóriákat, majd 100%-ban újjáépíti a keresési tsvectort és a 'documents' táblát. A kapcsolatok újra élnek.
